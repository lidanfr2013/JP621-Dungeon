# ТЗ №2: «Подземелье» - текстовый квест-движок с боевой системой

## 1. Суть проекта

Консольная текстовая игра (interactive fiction): игрок перемещается между
комнатами, собирает и использует предметы, разговаривает с персонажами и
сражается с противниками в пошаговом бою. Мир игры (карта комнат, предметы,
противники) описывается в JSON-файле как **контент**, а прогресс игрока
(текущая комната, инвентарь, здоровье) сохраняется в отдельный JSON-файл как
**сохранение**. Это разграничение (контент vs. сохранение) - часть задания,
а не опция.

Важно: это НЕ требование написать движок, способный загрузить произвольную
неограниченную игру - достаточно фиксированного, но нетривиального мира
(не менее 5 комнат, не менее 5 предметов, не менее 2 противников, см. п. 4),
прописанного в JSON.

## 2. Формат работы

Интерактивный режим (запуск и дальше - ввод команд в цикле, а не отдельные
вызовы из командной строки, в отличие от Проекта №1):

```
$ python main.py --new-game
$ python main.py --load save1.json
```

Внутри игры - текстовые команды, например:

```
> go north
> look
> inventory
> take sword
> use potion
> talk guard
> attack goblin
> save
> quit
```

Набор глаголов команд студент может адаптировать (можно на русском:
`идти`, `осмотреться`, `взять`, `атаковать` и т.д.), но сценарии из п. 3
обязательны.

## 3. Функциональные требования

1. **Перемещение по миру** - комнаты соединены переходами (например,
   north/south/east/west или произвольные именованные выходы); попытка
   пойти в несуществующем направлении - понятное сообщение, а не ошибка.
2. **Осмотр** - команда показывает описание текущей комнаты, видимые
   предметы и персонажей/противников в ней.
3. **Инвентарь** - просмотр текущего инвентаря игрока.
4. **Взять предмет** - переносит предмет из комнаты в инвентарь игрока.
5. **Использовать предмет** - эффект зависит от типа предмета (например,
   зелье лечит, ключ открывает проход, оружие можно экипировать - минимум
   2 разных типа предметов с разным поведением, см. п. 5).
6. **Диалог с NPC** - как минимум с одним неигровым персонажем можно
   поговорить и получить текст/подсказку/предмет.
7. **Бой** - пошаговая система: игрок и противник поочерёдно наносят урон;
   у обоих есть HP; бой заканчивается победой (противник исчезает из
   комнаты, возможен дроп предмета), поражением (игра сообщает о проигрыше
   и завершается либо предлагает загрузить сохранение) или бегством
   (если это реализовано - по желанию).
8. **Сохранение и загрузка** - команда `save` пишет текущее состояние
   (комната, HP, инвентарь, факты - например, какие противники уже
   побеждены) в JSON-файл сохранения; при запуске с `--load` состояние
   восстанавливается.
9. **Условие победы** - у игры должна быть достижимая финальная цель
   (например, дойти до определённой комнаты, победить конкретного
   противника, собрать определённый предмет) с соответствующим сообщением
   об окончании игры.
10. **Обработка ошибок** - некорректная команда, попытка использовать
    отсутствующий в инвентаре предмет, попытка атаковать при отсутствии
    противника в комнате и т.п. должны обрабатываться понятным сообщением,
    без падения программы.

## 4. Требования к содержимому мира (минимум)

- Не менее **5 комнат**, связанных между собой (не просто цепочка - хотя бы
  одно разветвление/выбор пути).
- Не менее **5 предметов** минимум 2 разных типов (см. п. 5).
- Не менее **2 противников**, отличающихся характеристиками (HP, урон) -
  на выбор студента, разное поведение в бою (см. п. 5) приветствуется, но
  не обязательно.
- Не менее **1 NPC** для диалога.

## 5. Требования к использованию ООП (обязательны все 4 принципа)

- **Абстракция.** Абстрактный базовый класс `Character` (`abc.ABC`) с
  абстрактными методами, например `attack(target)` и `is_alive()` (или
  свойством `is_alive`) - реализуются в подклассах. Аналогично рекомендуется
  (не обязательно) `Item` как абстрактный/базовый класс с абстрактным
  методом `use(player)`.
- **Инкапсуляция.** HP и прочие характеристики персонажей хранятся как
  защищённые атрибуты (`_hp`) с доступом через `@property`, сеттер не
  позволяет уйти в отрицательные значения или превысить максимум.
- **Наследование.** `Player`, `NPC`, `Enemy` (или конкретные виды
  противников) наследуются от `Character` и переопределяют/дополняют
  поведение. Для предметов - минимум 2 подкласса `Item` с разным поведением
  метода `use()` (например, `Potion` и `Weapon`/`Key`).
- **Полиморфизм.** Код боевой системы вызывает `attacker.attack(defender)`
  одинаково для игрока и для любого противника, не проверяя тип через
  `if isinstance(...)` в основной логике боя - разное поведение обеспечивают
  переопределённые методы, а не ветвление по типу в вызывающем коде.
  Аналогично `item.use(player)` должен работать одинаково для любого типа
  предмета, вызываемый из инвентаря.

Дополнительно приветствуется (не обязательно): композиция - `Inventory` как
отдельный класс, которым владеет `Player`; собственные исключения
(`ItemNotFoundError`, `RoomNotConnectedError` и т.п.).

## 6. Хранение данных (JSON как база данных)

Два раздельных JSON-источника - это ключевое архитектурное требование
проекта:

### 6.1. Контент мира - `data/world.json` (только чтение движком)

```json
{
  "rooms": {
    "entrance": {
      "description": "Вы стоите у входа в подземелье.",
      "exits": {"north": "hall"},
      "items": ["rusty_key"],
      "enemies": [],
      "npcs": []
    },
    "hall": {
      "description": "Большой зал с эхом шагов.",
      "exits": {"south": "entrance", "east": "armory"},
      "items": [],
      "enemies": ["goblin"],
      "npcs": ["old_guard"]
    }
  },
  "items": {
    "rusty_key": {"type": "key", "name": "Ржавый ключ", "opens": "armory_door"},
    "health_potion": {"type": "potion", "name": "Зелье лечения", "heal": 30}
  },
  "enemies": {
    "goblin": {"name": "Гоблин", "hp": 20, "damage": 4}
  },
  "npcs": {
    "old_guard": {"name": "Старый страж", "dialogue": "Берегись гоблинов в зале."}
  },
  "start_room": "entrance",
  "win_condition": {"type": "reach_room", "room": "throne_room"}
}
```

### 6.2. Сохранение - `data/save1.json` (чтение и запись движком)

```json
{
  "player": {
    "current_room": "hall",
    "hp": 76,
    "max_hp": 100,
    "inventory": ["rusty_key"]
  },
  "world_state": {
    "defeated_enemies": [],
    "taken_items": ["rusty_key"],
    "flags": {}
  },
  "saved_at": "2026-09-12T09:00:00"
}
```

Требования к работе с JSON:

- Загрузка мира и загрузка/сохранение прогресса реализуются через отдельные
  классы/модули (например, `WorldLoader` и `SaveManager`), а не смешанным
  кодом внутри игрового цикла.
- Повреждённый или отсутствующий файл сохранения/мира - понятное сообщение
  об ошибке, а не трейсбек.
- Структуру JSON студент может расширять под свою игру, но разделение
  «контент / сохранение» обязательно.

## 7. Рекомендуемая структура проекта

```
project/
├── main.py                  # точка входа, игровой цикл, парсинг команд
├── models/
│   ├── character.py          # Character (ABC), Player, Enemy, NPC
│   ├── item.py                # Item (ABC) и подклассы
│   └── room.py                 # Room
├── engine/
│   ├── world_loader.py         # чтение world.json -> объекты Room/Item/Enemy
│   ├── save_manager.py         # чтение/запись сохранения
│   └── combat.py                 # пошаговая боевая система
├── data/
│   ├── world.json
│   └── save1.json
├── README.md
└── requirements.txt
```

## 8. Нефункциональные требования

- Python 3.10+.
- Игра не должна падать с необработанным исключением при некорректном вводе
  игрока.
- Понятные текстовые сообщения (язык - на выбор студента, единообразно).
- README с описанием команд, примером карты мира и инструкцией запуска.
- Сторонние библиотеки не обязательны (можно `rich`/`colorama` для вывода -
  по желанию).

## 9. Примерный план на 2 недели

- **Дни 1–2:** проектирование классов (`Character`, `Item`, `Room`),
  набросок карты мира на бумаге, структура проекта.
- **Дни 3–5:** реализация модели персонажей и предметов (abstraction,
  encapsulation, inheritance), ручная проверка через `python -i`.
- **Дни 6–7:** `WorldLoader` - загрузка мира из JSON в объекты; заполнение
  `world.json` содержимым (комнаты, предметы, противники, NPC).
- **Дни 8–9:** игровой цикл, команды перемещения/осмотра/инвентаря/предметов.
- **Дни 10–11:** боевая система (полиморфный `attack()`), диалог с NPC,
  условие победы/поражения.
- **Дни 12–13:** сохранение/загрузка (`SaveManager`), обработка ошибок,
  README.
- **День 14:** финальное прохождение своей игры от начала до конца,
  подготовка к защите.

## 11. Идеи для дополнительных баллов (по желанию)

- Несколько сохранений (слоты), команда просмотра списка сохранений.
- Ветвящиеся диалоги с NPC (выбор реплик, влияющих на игру).
- Простая система уровней/опыта игрока.
- Разные типы противников с уникальным поведением в бою (не только цифрами).
- Простые unit-тесты (`unittest`/`pytest`) на боевую систему и загрузчик мира.
