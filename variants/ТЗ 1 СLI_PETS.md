# ТЗ №1: «Терравариум» — симулятор виртуальных питомцев в терминале

## 1. Суть проекта

Консольная утилита, позволяющая заводить, воспитывать и содержать виртуальных
питомцев разных видов. У каждого питомца есть характеристики (голод, энергия,
здоровье, настроение), которые меняются со временем и в зависимости от
действий пользователя (покормить, поиграть, уложить спать, полечить). Питомцы
разных видов ведут себя и реагируют на уход по-разному. Все данные хранятся
между запусками в JSON-файле.

Это НЕ игра с графикой и не игра в реальном времени с фоновым процессом —
время «тикает» по разнице между текущим моментом и временем последнего
взаимодействия (см. раздел 5).

## 2. Формат работы

Утилита запускается из терминала с аргументами командной строки (можно
использовать `argparse` или собственный парсер) либо как интерактивное
меню — на выбор студента, но должно быть явно описано в отчёте/README.

Примеры команд (вариант с `argparse`, командный стиль):

```
python main.py add-pet --name Рекс --species dragon
python main.py list
python main.py status --name Рекс
python main.py feed --name Рекс
python main.py play --name Рекс
python main.py sleep --name Рекс
python main.py heal --name Рекс
python main.py release --name Рекс
python main.py history --name Рекс
```

Конкретные названия команд и флагов студент может адаптировать, но набор
сценариев (п. 3) должен быть полностью покрыт.

## 3. Функциональные требования

1. **Завести питомца** — имя (уникальное) + вид из фиксированного списка видов
   (не менее 3 видов, см. п. 4).
2. **Список питомцев** — таблица/список: имя, вид, возраст (в игровых часах
   или днях с момента создания), краткий статус (жив/болен/спит).
3. **Статус питомца** — подробные характеристики: голод, энергия, здоровье,
   настроение, текущее состояние (бодрствует/спит/болен/мёртв).
4. **Покормить** — снижает голод, слегка повышает настроение. Если питомец
   спит — действие запрещено (с понятным сообщением об ошибке).
5. **Поиграть** — повышает настроение, расходует энергию, слегка повышает
   голод. Требует минимального уровня энергии.
6. **Уложить спать / разбудить** — во время сна энергия восстанавливается
   быстрее, здоровье слегка восстанавливается, но голод продолжает расти.
7. **Полечить** — доступно только если питомец болен; восстанавливает
   здоровье, требует ресурса (например, «аптечка», которая тратится —
   реализовать простой инвентарь ресурсов в отдельном JSON-разделе или файле).
8. **Естественное течение времени** — при каждом запуске утилита сравнивает
   текущее время с временем последнего действия над питомцем и «доначисляет»
   изменения характеристик (голод растёт, энергия падает и т.д.) пропорционально
   прошедшему времени. Если голод/энергия/здоровье выходят за критические
   пороги — питомец заболевает; если здоровье падает до нуля — питомец
   умирает (дальнейшие действия с ним, кроме просмотра истории, запрещены).
9. **История событий** — при каждом значимом действии (кормление, болезнь,
   смерть и т.д.) в питомца добавляется запись в лог с меткой времени;
   команда `history` показывает последние N событий.
10. **Отпустить питомца** — удаление питомца из базы с подтверждением.
11. **Обработка ошибок** — несуществующее имя, дублирующееся имя при
    создании, неверный вид питомца, действие над мёртвым/отсутствующим
    питомцем и т.п. должны выдавать внятные сообщения, а не трейсбек
    python.

## 4. Требования к видам питомцев (минимум 3 вида)

Каждый вид должен реально отличаться поведением, а не только именем. Пример
набора (можно предложить свой):

- **Дракон** (`dragon`) — медленно теряет энергию, но голод растёт быстро;
  особая способность «дыхание огнём» повышает настроение сильнее обычного.
- **Робо-пёс** (`robot`) — не «спит», а «заряжается» (энергия восстанавливается
  вместо сна, здоровье не восстанавливается сном); не болеет от голода, но
  может «сломаться» при нуле энергии.
- **Кот** (`cat`) — голод растёт медленно, но настроение падает быстрее и
  требует частой игры; во сне здоровье восстанавливается лучше остальных.

Значения коэффициентов студент подбирает и документирует самостоятельно.

## 5. Требования к использованию ООП (обязательны все 4 принципа)

Требование к ООП — центральная часть оценки. Ниже описано, **где именно**
каждый принцип должен быть виден в коде (студент не обязан копировать
структуру дословно, но принципы должны присутствовать по существу):

- **Абстракция.** Базовый класс `Pet` (или `AbstractPet`) — абстрактный
  класс через `abc.ABC`, содержащий как минимум один `@abstractmethod`
  (например, `make_sound()` и/или `special_ability()`), который каждый вид
  реализует по-своему. Создать экземпляр самого `Pet` напрямую должно быть
  невозможно.
- **Инкапсуляция.** Характеристики (голод, энергия, здоровье, настроение)
  хранятся как защищённые атрибуты (`_hunger` и т.п.) и доступны через
  `@property`, при этом **сеттеры обязаны валидировать границы** (например,
  значение не может быть меньше 0 или больше 100 — присвоение вне диапазона
  должно либо обрезаться, либо кидать исключение, это решает студент и
  описывает в коде).
- **Наследование.** Каждый вид питомца — отдельный класс, унаследованный от
  `Pet`, переопределяющий общее поведение (скорость роста голода, реакцию на
  сон и т.д.) через переопределение методов или атрибутов класса.
- **Полиморфизм.** Код, который вызывает `pet.feed()`, `pet.play()`,
  `pet.sleep()` и т.п., не должен знать о конкретном виде питомца — единый
  интерфейс, разное поведение. Явно продемонстрировать это, например, в
  команде `list`, где для питомцев разных видов вызывается один и тот же код.

Дополнительно приветствуется (не обязательно, на усмотрение студента):
композиция (например, отдельный класс `Inventory` для ресурсов лечения) и
собственные исключения (`class PetIsDeadError(Exception)` и т.п.).

## 6. Хранение данных (JSON как база данных)

Файл `data/pets.json` (путь может быть иным, но зафиксирован в README).
Пример структуры:

```json
{
  "pets": [
    {
      "name": "Рекс",
      "species": "dragon",
      "created_at": "2026-09-01T10:00:00",
      "last_updated": "2026-09-12T08:30:00",
      "stats": {
        "hunger": 42,
        "energy": 70,
        "health": 95,
        "mood": 60
      },
      "state": "awake",
      "history": [
        {"timestamp": "2026-09-12T08:30:00", "event": "fed", "details": "Голод снижен на 20"}
      ]
    }
  ],
  "resources": {
    "medkits": 2
  }
}
```

Требования к работе с JSON:

- Чтение/запись через модуль `json`, отдельный класс или модуль
  `Storage`/`Repository`, инкапсулирующий работу с файлом (не разбрасывать
  `open()`/`json.load()` по всему коду).
- Сохранение должно происходить после каждого изменяющего действия (либо
  атомарно — запись во временный файл и переименование, это плюс, но не
  обязательно).
- При отсутствии файла — создавать пустую базу автоматически, без падения
  программы.
- Некорректный/повреждённый JSON-файл должен обрабатываться с понятным
  сообщением об ошибке, а не трейсбеком.

## 7. Рекомендуемая структура проекта

```
project/
├── main.py                 # точка входа, разбор аргументов CLI
├── models/
│   ├── pet.py               # Pet (ABC) и подклассы видов
│   └── inventory.py         # (опционально) ресурсы/предметы
├── storage/
│   └── repository.py        # чтение/запись JSON
├── services/
│   └── pet_service.py        # бизнес-логика (кормить, играть, тикать время)
├── data/
│   └── pets.json
├── README.md
└── requirements.txt          # если используются сторонние библиотеки
```

Разбиение на файлы — рекомендация, не жёсткое требование, но логика
(классы), хранение (JSON) и интерфейс (CLI) должны быть разделены, а не
свалены в один файл.

## 8. Нефункциональные требования

- Код на Python 3.10+.
- Отсутствие падений программы с необработанным исключением при обычных
  сценариях использования и при вводе некорректных данных пользователем.
- Читаемые сообщения для пользователя (на русском или английском — на
  выбор, но единообразно).
- Наличие README с описанием команд и примером запуска.
- Использование сторонних библиотек, кроме стандартной библиотеки Python,
  не обязательно (кроме, например, `rich`/`colorama` для красивого вывода —
  можно, но по желанию).

## 9. Примерный план на 2 недели

- **Дни 1–2:** проектирование классов (`Pet` и наследники), диаграмма
  атрибутов/методов на бумаге или в README, заготовка структуры проекта.
- **Дни 3–5:** реализация модели питомцев (encapsulation, inheritance,
  abstraction), юнит-проверка вручную через `python -i` или простой скрипт.
- **Дни 6–8:** реализация хранилища (JSON), связка модели и хранилища,
  команды `add-pet`, `list`, `status`.
- **Дни 9–11:** команды `feed`, `play`, `sleep`, `heal`, `release`,
  реализация «доначисления» времени между запусками.
- **Дни 12–13:** история событий, обработка ошибок, полировка CLI, README.
- **День 14:** финальное тестирование сценариев, подготовка к защите.

## 11. Идеи для дополнительных баллов (по желанию)

- Несколько ресурсов/предметов (еда разного типа, игрушки) как отдельные
  классы с собственным эффектом.
- Собственные исключения вместо `ValueError`/сообщений в консоль.
- Команда экспорта статистики (например, самый старый питомец, средний
  уровень здоровья по всем питомцам).
- Цветной вывод в терминале.
- Простые unit-тесты (`unittest`/`pytest`) на модель питомцев.
