Задание 1

Терравариум

Консольная утилита для содержания виртуальных питомцев. У каждого — голод, энергия, здоровье и настроение, которые меняются со временем и от действий владельца. Данные живут в JSON-файле между запусками.

Суть проекта

Это не игра с графикой и не фоновый процесс в реальном времени — время «тикает» по разнице между текущим моментом и временем последнего взаимодействия с питомцем. Утилита запускается из терминала с аргументами командной строки (argparse или свой парсер) либо как интерактивное меню — формат выбирает студент, но описывает его в README.

пример вызовов
$ python main.py add-pet --name Рекс --species dragon
$ python main.py list
$ python main.py status --name Рекс
$ python main.py feed --name Рекс
$ python main.py play --name Рекс
$ python main.py sleep --name Рекс
$ python main.py heal --name Рекс
$ python main.py release --name Рекс
$ python main.py history --name Рекс

Названия команд и флагов можно адаптировать — набор сценариев ниже должен быть покрыт полностью, независимо от того, как он называется.

Что нужно реализовать

  1. Завести питомца — уникальное имя и вид из фиксированного списка (не менее 3 видов).
  2. Список питомцев — имя, вид, возраст с момента создания, краткий статус (жив / болен / спит).
  3. Статус питомца — подробные характеристики и текущее состояние: бодрствует, спит, болен, мёртв.
  4. Покормить — снижает голод, слегка поднимает настроение. Во сне действие запрещено, с понятным сообщением.
  5. Поиграть — поднимает настроение, тратит энергию, слегка повышает голод. Нужен минимальный уровень энергии.
  6. Уложить спать / разбудить — во сне энергия восстанавливается быстрее, здоровье слегка растёт, но голод продолжает копиться.
  7. Полечить — доступно только больному питомцу; восстанавливает здоровье и тратит ресурс («аптечка») из простого инвентаря.
  8. Течение времени — при каждом запуске утилита сравнивает текущее время с временем последнего действия и доначисляет изменения характеристик. Выход за критические пороги — болезнь; здоровье на нуле — смерть, дальше с питомцем нельзя ничего делать, кроме просмотра истории.
  9. История событий — каждое значимое действие (кормление, болезнь, смерть) пишется в лог с меткой времени; команда history показывает последние N записей.
  10. Отпустить питомца — удаление из базы с подтверждением.
  11. Обработка ошибок — несуществующее или повторяющееся имя, неверный вид, действие над мёртвым или отсутствующим питомцем — понятное сообщение, а не traceback.

Виды питомцев

Минимум три, и каждый должен реально отличаться поведением, а не только именем. Коэффициенты студент подбирает и документирует сам.

Драконdragon
Медленно теряет энергию, но голод растёт быстро. Особая способность «дыхание огнём» поднимает настроение сильнее обычного.
Робо-пёсrobot
Не спит, а заряжается — энергия восстанавливается вместо сна, здоровье сном не лечится. Не болеет от голода, но может сломаться при нуле энергии.
Котcat
Голод растёт медленно, но настроение падает быстрее и требует частой игры. Во сне здоровье восстанавливается лучше, чем у остальных.

Требования к ООП

Все четыре принципа обязательны и должны присутствовать по существу, а не для галочки.

Абстракция

Pet — абстрактный класс через abc.ABC, минимум с одним @abstractmethod (например, make_sound() и/или special_ability()). Создать экземпляр самого Pet напрямую нельзя.

Инкапсуляция

Голод, энергия, здоровье, настроение — защищённые атрибуты (_hunger и т.п.), доступ через @property. Сеттеры обязаны валидировать границы 0–100: обрезкой или исключением.

Наследование

Каждый вид — отдельный класс-наследник Pet, переопределяющий скорость роста голода, реакцию на сон и другое общее поведение.

Полиморфизм

Код, вызывающий pet.feed(), pet.play(), pet.sleep(), не должен знать вид питомца. Особенно заметно в команде list, где для всех видов вызывается один и тот же код.

Необязательно, но приветствуется: композиция (класс Inventory для ресурсов лечения) и собственные исключения (PetIsDeadError и подобные).

Хранение данных

JSON как база данных — файл data/pets.json (путь может быть иным, но зафиксирован в README). Чтение и запись — через отдельный класс/модуль Storage/Repository, а не разбросанные по коду open()/json.load(). Сохранение — после каждого изменяющего действия. Отсутствующий файл — создаётся пустая база автоматически; повреждённый JSON — понятное сообщение об ошибке, а не traceback.

data/pets.json
{
  "pets": [
    {
      "name": "Рекс",
      "species": "dragon",
      "created_at": "2026-09-01T10:00:00",

Рекомендуемая структура проекта

Разбиение на файлы — рекомендация, не жёсткое требование. Но логика (классы), хранение (JSON) и интерфейс (CLI) должны быть разделены, а не свалены в один файл.

project/
main.py                 # точка входа, разбор аргументов CLI
models/
  pet.py                # Pet (ABC) и подклассы видов
  inventory.py          # (опционально) ресурсы/предметы
storage/
  repository.py         # чтение/запись JSON
services/
  pet_service.py        # бизнес-логика: кормить, играть, тикать время
data/
  pets.json
README.md
requirements.txt         # если используются сторонние библиотеки

Нефункциональные требования

  • Python 3.10+.
  • Никаких падений с необработанным исключением при обычных сценариях и некорректном вводе.
  • Читаемые сообщения — на русском или английском, но единообразно.
  • README с описанием команд и примером запуска.
  • Сторонние библиотеки не обязательны — rich/colorama для вывода можно по желанию.

Идеи для дополнительных баллов

  • Несколько ресурсов/предметов (еда разного типа, игрушки) как отдельные классы с собственным эффектом.
  • Собственные исключения вместо ValueError/сообщений в консоль.
  • Команда экспорта статистики — например, самый старый питомец, средний уровень здоровья по всем питомцам.
  • Цветной вывод в терминале.
  • Простые unit-тесты (unittest/pytest) на модель питомцев.
